## Architecture (updated on Kamar's request: "backend se jodo, Python aur SQL ka use karo")
- **Backend = Python** (`server.py`, standard library + Piper) with **SQLite** (`db.py`, `data/piyu.sqlite3`): tables `docs, blocks (+FTS5 full-text index), tasks, tombstones, blobs, meta`.
- Browser keeps a local copy in IndexedDB (works offline) and syncs to the backend (`/api/state`, last-write-wins per item, tombstones for deletes).
- SQL does the work the browser can't do cheaply: `/api/search` (FTS5 + bm25, Hindi/English/₹), `/api/stats` (dashboard numbers, streak, on-time %), `/api/blob/<id>` (attachments as BLOBs).
- One file (`piyu.sqlite3`) = complete backup; VPS-ready (env config, token required when public).

## 1. Storage backbone + backup/sync
**Why:** localStorage is 5 MB, per-browser, lost on cache clear. OCR text + attachments need far more.
**Design**
- `store.js`: async key-value API over **IndexedDB** (`state`, `blobs` stores); one-time migration from `localStorage['piyu.v1']`.
- `server.py`: `GET/PUT /api/state` (JSON, atomic write to `data/state.json`), `GET/PUT/DELETE /api/blob/<id>`; every write is stamped `updatedAt`.
- Sync: on save → debounce 1.5 s → PUT if server reachable; on load and every 60 s → GET, **last-write-wins per task (by `updatedAt`)**, deletions kept as tombstones so a deleted task does not come back.
- Manual: **Export backup** (`piyu-backup-YYYY-MM-DD.json`, includes attachments as base64) / **Import backup** (merge or replace).
- Settings shows sync status (last sync time, offline/online).
**Files:** `store.js` (new), `app.js`, `server.py`, `index.html` (Settings card).
**Acceptance test:** (a) reload keeps data; (b) clear localStorage/IDB in browser A → reopen → data restored from server; (c) two browser profiles edit different tasks → both changes present; (d) delete in A → not resurrected by B; (e) export → reset → import → identical state; (f) 15 MB document stored OK.
**Limits:** sync works between devices that can reach the same `server.py` (same Wi-Fi / your own tunnel). No cloud account.

## 2. Recurring alarms
**Design:** task gets `repeat: {type:'daily'|'weekly'|'monthly'|'interval', days:[0-6], every:n, until?}`. When a recurring task is marked done/missed, spawn the next occurrence (keep history for stats). Parse from text: "every day/har roz/daily", "every Monday/har somvar", "monthly/har mahine", "weekdays". Edit dialog gets a Repeat selector. ICS export writes `RRULE`.
**Acceptance:** unit tests for next-occurrence (month-end, DST-free local time, weekly multi-day); doc text "every Monday 9 AM" creates a weekly task; completing it schedules next Monday; ICS contains RRULE.

## 3. Priority + dependencies
**Design:** `priority` 1–4 computed (`urgent/critical/zaroori/important/deadline/ASAP` words, nearness of deadline, rule-sections) and user-overridable. Dependency detection: "Step N" after "Step N-1" in same section; phrases "after/before/tab tak/pehle/jab … ho jaye". A blocked task shows "🔒 pehle: <task>" and Piyu's "abhi kya karu?" picks by **score = priority + urgency − blocked**. Sort options: time / priority.
**Acceptance:** on the Hinglish PDF, Step 4 is blocked until Step 3 done; "abhi kya karna hai" never returns a blocked task; priority badge visible & editable.

## 4. Subtasks + guided mode
**Design:** each task's text is split into `subtasks[]` (sentences / "Step:" items / bullets) with checkboxes and progress bar. **Guide mode** ("Guide karo"): Piyu speaks one step, waits; voice/buttons "ho gaya / next / repeat / peeche / roko". Finishing the last step offers to mark the task done.
**Acceptance:** guided flow walks Step 3 of the PDF start→finish by buttons and by typed commands; progress persists after reload.

## 5. Links & attachments
**Design:** URLs in task text become tappable chips (open new tab); user can attach files/photos to a task (stored as blobs via store.js, size shown, open/download/delete). Task cards show 📎 count.
**Acceptance:** attach a PNG + PDF → reload → still there → open; delete works; backup includes them.

## 6. Morning plan + night summary
**Design:** configurable times (default 08:00 and 21:30). Morning: spoken + notification "aaj N kaam, sabse pehle X at T, blocked/overdue Y". Night: done vs pending, streak, tomorrow's first task. Card on Home; replayable by voice ("aaj ka plan"). Fires once per day (persisted marker), catch-up if the app opens within 3 h after the time.
**Acceptance:** fake-clock test triggers each once; no double fire after reload.

## 7. Voice moods + focus mode / quiet hours
**Design:** Piper params per mood — `calm` (info), `urgent` (alarm: faster, brighter), `gentle` (night). Focus mode (toggle + timer) and quiet hours (e.g. 23:00–07:00): pre-alerts become silent notification + toast; final alarm still rings unless "hard quiet" is chosen. Home shows focus state.
**Acceptance:** mood params change the `/tts` query (verified in network log); quiet hours suppress speech but not the record of the alert.

## 8. Progress dashboard
**Design:** new "Progress" tab: done today/week, on-time %, missed, streak, per-day bar chart (14 days), by-section breakdown. Pure inline SVG, dark/light aware (use the `dataviz` skill rules). Data from `task.doneAt`, history of recurring tasks.
**Acceptance:** numbers match a hand-built fixture; empty state is graceful.

## 9. OCR (scanned PDF, photos, camera)
**Design:** vendor `tesseract.js` (worker + wasm core) and `eng` + `hin` traineddata into `vendor/ocr/` (fully offline). Image files (`.png .jpg .webp`) and camera capture (`<input capture>`) → OCR → blocks. Scanned PDF (no text layer) → render each page with pdf.js to canvas → OCR. Progress bar per page; cancellable.
**Acceptance:** a generated image with Hindi+English text is read back with ≥90 % of words; a scanned (image-only) PDF is read; no network requests during OCR.
**Limits:** handwriting and low-quality photos are unreliable; OCR is slow on big PDFs (≈2–5 s/page).

## 10. "Hey Piyu" wake word
**Design:** always-listening toggle. **v1:** Chrome `SpeechRecognition` continuous mode with auto-restart, wake phrases "hey piyu / ae piyu / हे पीयू / पीयू"; command captured after the phrase, chime on wake, then normal chat path. **Honest limit:** Chrome's recogniser sends audio to Google's free speech service (no key, no cost, **not offline**), needs mic permission and the tab open. Optional v2 if time: offline Vosk-WASM.
**Acceptance:** with a simulated recogniser feed, phrase detection triggers on variants and ignores unrelated speech; mic auto-restarts after `onend`; visible "listening" indicator; one-tap off.

## 11. Optional offline AI answers (Ollama)
**Design:** `server.py` proxies `/api/ai` → `http://127.0.0.1:11434`. If Ollama + a model are present, chat answers use retrieval (top document blocks) + local LLM with a strict "answer only from the document, say when unknown" prompt, streamed to the UI; otherwise silently falls back to current keyword answers. Settings shows detected model / install hint (`ollama pull qwen2.5:3b`). Install Ollama only if it can be done without sudo; otherwise ship code + instructions.
**Acceptance:** with a mock Ollama endpoint, streaming answer renders and is spoken; with none, chat works as before; the prompt contains only retrieved blocks.
**Limits:** ~2 GB free RAM now → recommend 1.5–3 B models; quality < cloud LLMs.

## 12. More languages (bn, mr, ur + hi/en)
**Design:** move all UI strings + spoken templates into `i18n.js` packs; language switcher; Piper voices downloaded to `voices/` (`bn_BD`, `mr_IN`, `ur_PK` — chosen from the repo listing); date/time words per language; intent regexes extended per language. Documents in any language still parse (Unicode-aware tokens).
**Acceptance:** switching language re-renders every screen with no missing keys (script checks every key exists in every pack); each voice returns audio from `/tts`.
**Limits:** intent keywords for bn/mr/ur are a first pass; quality of translations to be reviewed by a native speaker.

## 13. Piyu's Mind — memory, learning, emotions, questions, voice self-tuning (requested by Kamar)
**What was asked:** its own memory; learns every day from the user; learns tone and way of speaking and answers in the same style; understands emotion and situation; asks questions; improves its own voice tone.
**What it will honestly be:** no neural training. It is a *local, transparent, user-controlled* adaptive system:
- **Memory** (SQL + synced): `facts` (name, habits, preferences — said or asked), `episodes` (recent chats/events), `days` (daily summaries after consolidation), all viewable / editable / deletable in a "🧠 याददाश्त" screen; global switch "learning on/off" and "forget everything".
- **Tone learning:** every user message is analysed (Hindi/Hinglish/English mix, script, formality, politeness, length, emoji, exclamations, slang, address terms). Moving averages form a *style profile*; replies are re-shaped to it (address term, brevity, register, script Roman/Devanagari, emoji) — the rule-based replies only; with Ollama the profile is also given to the LLM.
- **Emotion + situation:** lexicons for joy / sadness / anger / stress / tiredness / excitement / gratitude / confusion / loneliness in Hindi, Hinglish, English (+ intensity from !!, CAPS, repeats), combined with context (time of day, overdue count, streak, focus/quiet) → empathetic openings, gentler/cheerful voice mood, smaller next-step suggestions.
- **Questions:** a rate-limited bank (max 1 per 4 h, 3 per day, never in focus/quiet/alarm/guide, never repeats an answered one) — name/address preference, wake/sleep time, best reminder lead time, mood check-in, "why was task X skipped", weekly goal. Quick-reply chips; answers become facts.
- **Daily learning pass (night):** stats → insights (e.g. "you finish most tasks 5–7 PM", "10-minute alerts are mostly snoozed") → **asked as questions; a behaviour changes only after the user says yes**.
- **Voice self-tuning:** 👍/👎 on Piyu's replies, spoken feedback ("dheere bolo", "tez bolo", "achhi awaaz") and implicit signals (repeat requests, quick stop) nudge speed / expressiveness / pitch **per situation** (day / evening / night × calm / stressed / happy) within ±20 % bounds; visible + resettable.
**Limits:** understanding is lexicon/rule based (can misread sarcasm, mixed emotions, new slang); it needs days of use to show; nothing leaves the machine.
**Acceptance tests:** analyzer tables per emotion/language; profile converges on synthetic casual-Hinglish vs formal-English users; style transforms; fact extraction; question scheduler rules; consolidation; recall; voice-preference learning bounds/direction; nightly insights from a fixture history; privacy (off = nothing stored, forget-all clears, sync merge across two devices); browser flows (stressed message → empathy + gentler voice params; question asked → answered → fact used later; thumbs-down slows voice; memory screen edit/delete).

## 14. Web fallback + self-learning knowledge base (requested by Kamar: "document me jawab na ho to Google/ChatGPT/search engine se khoj kar jawab do, API cost zero")
**Honest constraint:** Google search and ChatGPT have **no free official API** (and scraping them breaks their terms and gets blocked), so they are *not* called. Zero-cost sources used instead: **Wikipedia** (hi/en REST, no key), **DuckDuckGo** (Instant Answer JSON + HTML results, no key), and an optional **self-hosted SearXNG** (`PIYU_SEARXNG`) which meta-searches Google/Bing/etc. for free. "Google पर खोलें" / "ChatGPT में पूछें" buttons open the browser (manual, free).
**Design:** answer order = rule intents → document (with a relevance gate so a weak keyword hit no longer counts) → own memory/knowledge base → web → honest "not found" + open-in-browser links. Server `web.py`: backends, SSRF-safe page fetch (public hosts only, size/time caps), readability-lite extraction, SQLite cache with TTL, per-IP rate limit. Synthesis: local Ollama if present, otherwise extractive summary of the best sentences; **always shows sources**. Web use is **opt-in** (queries leave the machine) with a visible 🌐 label. Good answers (👍) are saved to a local knowledge base and answered from memory next time — so it improves itself and stops needing the web.
**Acceptance tests:** backend parsers on saved fixtures; SSRF cases (localhost, 10.x, 169.254, file://, redirects to private) blocked; caps/timeouts; cache hit = no network; extractive summary relevance; relevance gate; answer-order tests in browser with mock web servers; opt-in off = zero requests; offline → graceful; 👍 stores KB and the repeat question is answered without web; live smoke test against Wikipedia (skipped if no internet).

## 15. Android APK
**Design:** Capacitor wrapper of the web app + **native alarm scheduling** (`@capacitor/local-notifications` exact alarms, full-screen intent, boot reschedule) so alarms ring with the app closed / phone locked. The Piper server can't run on the phone → APK uses **Android's TTS** (or connects to Piyu server on LAN when available). Download JDK 17 + Android cmdline-tools + platform/build-tools into `~/piyu-android-tools`; build debug APK → `dist/piyu-debug.apk`.
**Acceptance:** APK builds; installs on an emulator/phone if available; schedules a notification 1 min ahead and it fires with the app closed. If no device/emulator is available here, I will say clearly that the alarm-with-app-closed test was **not** run on hardware.
**Limits:** debug-signed APK (sideload); Play-Store release needs your own signing key. Battery-optimisation settings on some phones (Xiaomi/Oppo) must be set to "no restrictions".

## 16. VPS-ready hosting kit (added by request)
**Goal:** everything is built and tested on localhost first, but nothing may be hard-wired to localhost, so the same folder can be copied to a VPS.
**Rules applied while building every feature**
- Config only via environment: `PIYU_HOST`, `PIYU_PORT`, `PIYU_DATA` (data dir), `PIYU_TOKEN` (required whenever host ≠ 127.0.0.1 — server **refuses to start** public without a token).
- All URLs relative (`/api/...`, `/tts`) — no `localhost` in client code. Service worker + PWA + mic + notifications + wake word need **HTTPS**, so the kit ships a reverse-proxy config.
- Server hardening: `/tts` text length cap + simple per-IP rate limit, request-size caps (already), constant-time token compare, `Cache-Control: no-store` on API, no directory listing, hidden `data/ voices/ .venv/ server.py`.
- Piper on a VPS: needs ~1.5 GB RAM for hi+en voices (lazy-load per language, unload idle) → document minimum plan (2 vCPU / 2 GB). Ollama (feature 11) stays **optional** and is not expected on a small VPS.
- APK (feature 13) gets a "Server URL" setting so it can use the VPS for sync + Piper voice, and falls back to Android TTS offline.
**Deliverables (`deploy/`)**: `Caddyfile` (auto-HTTPS), `piyu.service` (systemd, non-root user), `deploy.sh` (rsync + venv + piper + voices + enable service), `.env.example`, `DEPLOY.md` (step-by-step: DNS, firewall, token, backups, updates).
**Acceptance:** run the server with `PIYU_HOST=0.0.0.0` without a token → refuses; with token → API 401 without it, 200 with it; hidden paths 404; rate limit returns 429; a Caddy-less dry run of `deploy.sh --check` lists every step. (Real VPS deploy is done by Kamar; I will not claim it was tested on a real VPS.)
